## What this project is

A native in-process COM revocation provider for **AD CS Online Responder** (`ocspsvc.exe`).
It answers OCSP from a snapshot of the **CA certificate database** instead of a CRL, so a
revocation shows up in about a minute without waiting for CRL publication.

`CDBRP` = **C**A **D**atabase **B**ased **R**evocation **P**rovider.

## What is in scope

- The provider itself (`src/native/OcspDbProvider.cpp`), the shared configuration model
  (`src/native/OcspDbConfig.*`), the configuration tool (`src/native/OcspConfig.cpp`)
- The installer (`src/setup/`) and the PowerShell scripts (`scripts/`)
- Documentation, including the reverse-engineering notes that explain the COM contract

**Out of scope:** the responder service itself, IIS/OCSP ISAPI, CA database semantics, and
anything that requires shipping Microsoft binaries — this repository deliberately contains
none.

## Build

Requirements:

| Need | Version |
|---|---|
| Visual Studio | 2019 or 2022 with the C++ desktop workload (for x86 and ARM64: those toolchains too) |
| Windows SDK | 10.0.17763 or newer |
| PowerShell | 5.1 (Windows PowerShell) and/or 7.x |
| OS | Windows 10 / Server 2016 or newer to build; Windows 7 / Server 2008 R2 or newer to run |

```powershell
pwsh -File scripts/build.ps1              # x64 into out\x64
pwsh -File scripts/build.ps1 -Arch x86    # also x86, arm64
```

The build locates Visual Studio with `vswhere` and sets up `vcvars` itself, so it works from
a plain shell — no "Developer Command Prompt" needed.

## Test

```powershell
pwsh -File scripts/test.ps1
```

This builds, then runs 20 assertions against a synthetic snapshot: resource presence, the
provider's COM surface, per-CA configuration merging, serial normalization, and a round trip
where the configuration tool writes `provider.ini` and the provider reads it back through COM.

**No administrator rights and no certificate is required** — the harness loads the freshly
built DLL by path and points the provider at a temporary install directory through the
`OCSPDBPROVIDER_DIR` environment variable.

A pull request is expected to keep this suite at 20/20. If you add behaviour, add an
assertion for it.

## Ground rules for changes

These are the things that break deployed systems, so treat them as contracts:

1. **Do not change the binary identity.** CLSID `{7B0C4B1E-93A1-4C0F-9E52-0D2A6A5B41C9}`,
   the ProgID, `OcspDbProvider.dll` and the install layout must stay as they are. Renaming the
   project is fine (it has happened); renaming the COM class is not.
2. **`provider.ini` stays a superset.** New keys are fine, new sections are fine, but an
   existing file must keep working untouched. The same goes for the snapshot format.
3. **No new runtime dependencies.** The provider is loaded into `ocspsvc.exe`; adding a DLL
   that might be missing on a server is a support incident. The setup is statically linked
   (`/MT`) for the same reason.
4. **Never block the responder.** `VerifySerialNumber` is on the OCSP hot path. File access is
   cached and reloads are rate-limited; no network calls, no user interaction, no dialogs.
5. **Keep secrets and binaries out of the repository.** No CA private keys, no snapshots, no
   compiled artefacts (`out/`, `dist/` are already ignored).

### Encoding rules (these bite silently)

- **PowerShell scripts must stay ASCII-only.** Windows PowerShell 5.1 reads `.ps1` as ANSI
  when the file has no BOM, so a stray Chinese comment turns into mojibake and occasionally
  into a parse error. Comments in scripts are English for this reason.
- **`.rc` files must stay UTF-16LE with a BOM.** `rc.exe` decides the encoding from the BOM.
  `.gitattributes` marks `*.rc` as `-text` so git never rewrites their bytes; keep it that way.
- **`rc.exe` cannot resolve resource paths containing non-ASCII characters.** That is why the
  installer build stages its payload under `%TEMP%` with an ASCII-only name.

## Pull requests

1. One topic per pull request.
2. Describe the problem before the fix, and say how you verified it (command output is ideal).
3. Mention user-visible changes so `docs/RELEASE-NOTES-<version>.md` can pick them up.
4. If you change behaviour, say what happens to an **already deployed** installation.

Commit messages: a short imperative subject line, then a body explaining *why*. Squashing is
fine; the release notes are generated by hand anyway.

## Reporting bugs

Use the issue templates. The single most useful thing you can attach is the status page:

```powershell
& "$env:ProgramData\OcspDbProvider\uitest.exe" info -ca '<CA name>'
& "$env:ProgramData\OcspDbProvider\OcspConfig.exe" --dump
```

The first prints the snapshot path the provider actually resolved, whether the file exists,
its size and how many rows parsed — that answers most "it shows 0" reports immediately.

**Please do not open a public issue for a security problem** — see [SECURITY.md](SECURITY.md).
